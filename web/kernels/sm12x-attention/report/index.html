0. Scope, method, and how to read the labels

Scope. Every attention kernel that vLLM, SGLang or FlashInfer can run on compute capability 12.0 (sm_120: RTX PRO 6000 Blackwell, RTX 5090) and 12.1 (sm_121: DGX Spark GB10), what each kernel does internally, what is unfinished, and what is worth researching.

Method. Six repositories were cloned and read at the commits below. NVIDIA's PTX manual, Blackwell tuning guide and CUDA programming guide were read from docs.nvidia.com. Pull requests and issues were read through the GitHub API. No code was compiled or executed and no GPU was used. Every performance number in this report is a claim made by a pull-request or issue author.

1. Summary of findings

  1. Both engines default to FlashAttention-2-class kernels on SM12x. vLLM selects FLASH_ATTN running FA2; SGLang selects FlashInfer's fa2. Neither default uses a kernel written for these GPUs.
  2. vLLM's default changes with the model configuration. FA2 fails validation for an FP8 or NVFP4 KV cache, attention sinks, or a multimodal prefix. vLLM then falls through to FLASHINFER, which on SM12x pairs FlashInfer's native prefill with the XQA decode kernel.
  3. Three kernel families were written specifically for SM12x. FlashInfer's b12x paged attention (reachable from vLLM), SGLang's fa4_sm120 kernels (reachable from SGLang), and an unmerged set of upstream FlashAttention pull requests. All three use warp-level mma.sync. All three use TMA for at least one path.
  4. FA2 on SM12x runs with tiles tuned for A100 and H100. No file in FA2 tests for capability 12. Head dimension 128 gets a 128×64 tile with 4 warps, which is 64 KB of shared memory.
  5. Upstream FlashAttention-4 on SM120 is a 61-line subclass of the Ampere kernel. It uses cp.async, one pipeline stage and no TMA. It rejects paged KV, split-KV, FP8 and learnable sinks. vLLM's bundled fork additionally reports FA4 as unsupported unless the capability major is exactly 10.
  6. b12x paged decode already does page-aligned TMA. The page id is a tensor coordinate, the page size must be a multiple of the KV tile, and there is one block-table lookup per tile. b12x paged prefill does not: it uses per-thread 16-byte cp.async with a per-row page lookup, except for one shape.
  7. Native FP8 tensor-core multiply exists on SM12x and is mostly unused. b12x has it behind an environment variable. Upstream and SGLang have it in open pull requests that report 1.7× to 2.0× over BF16.
  8. Public benchmark numbers exist, and they are modest for BF16. On an RTX PRO 6000, the new BF16 kernels are reported at roughly 1.1× to 1.2× over FA2. The large reported gains are for FP8, for decode against the unoptimized upstream FA4, and against Triton.
  9. The DGX Spark is admitted but not tuned. b12x's tile specializations are keyed on exactly (12, 0). SGLang's split-KV latency model was fitted on 110-SM and 188-SM discrete cards. One FA2 tile fix explicitly excludes 12.1.
  10. Shared memory per SM on capability 12 is very likely 100 KB, not 128 KB. NVIDIA's tuning guide says 128 KB. Its programming guide says 100 KB and gives 128 KB as the unified L1/shared data cache, whose largest shared-memory carveout is 100 KB. Both agree on 99 KB per thread block, which is 100 KB minus the 1 KB CUDA reserves per block. Because of that reservation, two 64 KB blocks do not fit on one SM under either figure; two blocks fit only at 49 KB (50,176 B) each or less. Neither guide lists capability 12.1 separately.

2. The hardware target: instruction set and resource limits

2.1 The tensor-core instruction: mma.sync only

Conclusion. SM12x has no warpgroup instruction and no tensor-memory instruction. The only tensor-core instruction is the warp-level, register-operand mma.sync.

  • wgmma is Hopper-only. PTX: wgmma.mma_async "Requires sm_90a" [DOC] [S1 §9.7.17.5.2].
  • tcgen05 is data-center Blackwell only. PTX lists sm_100a, sm_101a and the sm_100f / sm_110f families; no SM12x target [DOC] [S1 §9.7.18.10.10.1].
  • CUTLASS gates both by equality. CUTLASS_ARCH_MMA_SM90_ENABLED requires __CUDA_ARCH__ == 900; CUTLASS_ARCH_MMA_SM100_ENABLED requires == 1000 [SRC] cutlass/include/cutlass/arch/config.h:45, 89.
  • CUTLASS's README states the consequence: "kernels compiled for Blackwell SM100 architecture with arch conditional features (using sm100a) are not compatible with RTX 50 series GPUs" [SRC] cutlass/README.md:331-334.

What mma.sync offers on SM12x:

Variant Shape Operands Target needed Source
BF16 / FP16 m16n8k16 16-bit baseline sm_120 ("requires sm_80 or higher") [S1 §9.7.16.5.14]; cute/arch/mma_sm80.hpp:39, 239
FP8, legacy form m16n8k32 .e4m3, .e5m2 baseline sm_120 ("requires sm_89 or higher") [S1]; cute/arch/mma_sm89.hpp:50, 79

Two consequences for attention:

  • A BF16 attention kernel needs no special target. The Ampere atom works on plain sm_120.
  • A native FP8 attention kernel is possible on plain sm_120 through the legacy m16n8k32 form. The .kind forms need the a or f target [INF from the PTX target notes].

CUTLASS ships no BF16 reference kernel for SM120. Its SM120 builder asserts "SM120 TmaWarpSpecialized builder currently only supports F8F6F4 MMA" [SRC] cutlass/include/cutlass/gemm/collective/builders/sm120_mma_builder.inl:80. A BF16 attention kernel therefore combines the Ampere atom with the SM120 TMA scaffolding by hand.

2.2 Operand path: shared memory → ldmatrix → registers

On Hopper, wgmma reads operands directly from shared memory through a descriptor. On SM12x every operand must first be copied into registers.

  • CUTLASS's SM120 mainloop asserts the MMA fragments are not descriptor iterators, then copies: "copy smem->rmem for A/B operand" before cute::gemm [SRC] cutlass/include/cutlass/gemm/collective/sm120_mma_tma.hpp:153, 511-523.
  • Each mma.sync atom holds 4 A registers, 2 B registers and 4 accumulator registers per thread [SRC] cute/arch/mma_sm120.hpp:57-60.
  • The limit is 255 registers per thread [DOC] [S2 §1.4.1.1].

Consequence [INF]. Operand fragments compete with accumulators for the register budget. This is the register pressure that Hopper and data-center Blackwell kernels avoid, and it bounds how many MMA atoms a warp can hold live.

ldmatrix variants: the classic m8n8 16-bit form is baseline. The m16n16 transposing 8-bit form and the sub-byte FP4/FP6 forms need sm_120a or sm_120f [DOC] [S1 §9.7.16.5.15].

2.3 TMA: available, without multicast

Conclusion. TMA and mbarrier are baseline features on SM12x. Cluster multicast is not available.

  • cp.async.bulk.tensor: "Requires sm_90 or higher." The multicast qualifier lists sm_90a, sm_100*, sm_103*, sm_110* and no SM12x target [DOC] [S1 §9.7.10.28.5.3].
  • CUTLASS emits a CTA-local destination on SM120 (.shared::cta.global) instead of the cluster form [SRC] cute/arch/copy_sm90_tma.hpp:59-61.
  • CUTLASS asserts a 1×1×1 cluster: "no programmatic multicast on this arch" [SRC] sm120_mma_builder.inl:84.
  • CUTLASS's SM120 GEMM uses PipelineTmaAsync, 8 MMA warps and one mainloop load warp, 384 threads in total [SRC] cutlass/include/cutlass/gemm/kernel/sm90_gemm_tma_warpspecialized_cooperative.hpp:115-125.
  • setmaxnreg (moving registers from the loader warp to the math warps) is available with sm_120a or sm_120f [DOC] [S1 §9.7.21.5].

2.4 Memory proxies and fence.proxy.async

Ordinary loads and stores use the "generic proxy". TMA uses the "async proxy". PTX: "Accessing the same memory location across multiple proxies needs a cross-proxy fence" [DOC] [S1 §9.7.10.28.2].

Two directions matter:

  • TMA write, then ordinary read. No explicit fence is needed: "The completion of a cp{.reduce}.async.bulk operation is followed by an implicit generic-async proxy fence" [DOC] [S1 §9.7.10.28.2].
  • Ordinary access, then TMA access to the same location. A fence is required. CUTLASS's epilogue does this before a TMA store: fence_view_async_shared(); // ensure smem writes are visible to TMA [SRC] cutlass/include/cutlass/epilogue/collective/sm90_epilogue_tma_warpspecialized.hpp:736-737. It also fences before releasing a consumed stage back to the producer [SRC] same file :817.

The second case is the one FlashInfer issue #7675 reports for the b12x GEMM (section 8.3).

The per-SM figure is very likely 100 KB [INF]. Four observations point the same way:

  1. Programming guide Table 35 gives capability 12.x a 128 KB unified data cache with shared-memory carveouts of 0, 8, 16, 32, 64 and 100 KB. No supported configuration gives kernels 128 KB of shared memory [DOC] [S3].
  2. On every other capability NVIDIA documents, the per-block limit is the per-SM limit minus the 1 KB CUDA reserves per block: 100 and 99 KB on 8.9, 228 and 227 KB on 10.0 [DOC] [S2 §1.4.2.3] [S35 §1.4.2.2]. The programming guide's 100 and 99 KB for 12.x fit that rule. The tuning guide's 128 and 99 KB do not.
  3. The 12.x row of Table 35 is identical to the 8.9 (Ada) row, and the Ada tuning guide says 100 KB per SM [DOC] [S35 §1.4.1.1].
  4. A microbenchmark study of GB203 (the RTX 5080/5090 die) reports 128 KB of combined L1 and shared memory per SM, of which about 99 KB can be allocated as shared memory [S36].

The tuning guide's 128 KB is most likely the unified-cache figure under the wrong label. None of these is a device query; section 11.3 gives the query that settles it.

Both readings give the same residency for every tile in this report [CALC]. A block occupies its shared memory plus the 1 KB reservation, so two blocks fit when 2 × (bytes + 1,024) ≤ the per-SM figure. That allows at most 50,176 B (49 KB) per block at 100 KB and 64,512 B at 128 KB. A 64 KB block needs 2 × 66,560 = 133,120 B, which exceeds 131,072 B, so two 64 KB blocks fit under neither figure. (An earlier version of this section said they fit under the 128 KB reading; that ignored the reservation and contradicted the table in section 3.) The two readings differ only for blocks between about 49 KB and 63 KB. Kernels that read the limit at run time (b12x, FlashInfer's fa2) adapt to whichever is true. Kernels that assume a count (FA2's split heuristic hard-codes two blocks per SM) do not. Neither guide lists capability 12.1 separately, so applying these numbers to the DGX Spark is an inference.

The 48-warp limit is a second ceiling. A 128-thread block is 4 warps, so at most 12 blocks fit by warp count. A 384-thread block is 12 warps, so at most 4. With 24 blocks per SM, two-warp blocks reach the 48-warp limit exactly; one-warp blocks hit the block limit first.

3. The common anatomy of an SM12x attention kernel

Every kernel in section 4 is a variation on one loop. Knowing the loop makes the differences legible.

For each tile of query rows, and for each tile of KV columns:

  1. Stage K. Move a K tile from GPU memory into shared memory, by TMA or by cp.async. For a paged cache, resolve the page first.
  2. Load fragments. ldmatrix the Q and K tiles from shared memory into registers.
  3. QK multiply. mma.sync produces the score tile S = QKᵀ in accumulator registers.
  4. Mask and online softmax. Apply causal, window and sink terms. Update each row's running maximum and running sum, and rescale the output accumulated so far.
  5. Stage V (often overlapped with step 3).
  6. PV multiply. Convert the probabilities P to the operand type, then mma.sync accumulates O += PV.

After the last KV tile, normalize O and write it out. For split-KV, write an unnormalized partial O and a log-sum-exp per row, and let a second kernel merge.

The design choices that distinguish kernels:

Choice Options seen on SM12x
Staging cp.async per thread; TMA issued by a math warp; TMA issued by a dedicated loader warp
Pipeline depth 1 stage is the norm at 99 KB; 2 stages for small head dimensions
Warp roles every warp does QK then PV; or separate QK warps and PV warps exchanging P through shared memory
Tile shape from 16×64 for decode up to 128×128 for small-head-dimension prefill
Where P lives registers (the usual choice), or shared memory when QK and PV warps are separate
Paged cache per-row page lookup; per-thread lookup with contiguous tile; page id as a TMA coordinate
Decode parallelism split along KV with an LSE merge; or one block per request
FP8 KV convert to 16-bit after load; or multiply FP8 operands directly

Shared-memory arithmetic [CALC]. With 16-bit elements, one stage, and Q, K and V all in shared memory, the bytes are 2 × (tile_m × d + tile_n × d + tile_n × d_v):

Head dim Tile (m×n) Bytes Under 101,376? Two per SM? (2 × (bytes + 1,024) ≤ 102,400; same answer at 128 KB)
64 128×128 49,152 yes yes
128 128×64 65,536 yes no (133,120 needed)
128 64×64 49,152 yes yes

4. Kernel-by-kernel internals

4.1 FlashAttention-2 (CUDA C++)

Role. vLLM's automatic choice on SM12x, through its bundled vllm_flash_attn.

  • MMA. SM80_16x8x16_F32F16F16F32_TN or the BF16 variant, for any architecture ≥ 800 [SRC] csrc/flash_attn/src/kernel_traits.h:29-34.
  • Staging. SM80_CP_ASYNC_CACHEGLOBAL<cute::uint128_t>, sequenced with cp_async_fence() and cp_async_wait<0>(). No TMA anywhere [SRC] kernel_traits.h:125-129; flash_fwd_kernel.h:261-409.
  • Tile selection has no SM12x branch. The only capability test is bool is_sm8x = cc_major == 8 && cc_minor > 0 [SRC] csrc/flash_attn/src/flash_fwd_launch_template.h:251-265. Capability 12 fails it and takes the branch commented "good for H100, A100" [SRC] :272.

Tiles a capability-12 device receives [SRC] flash_fwd_launch_template.h:200-321:

Head dim Tile, warps Shared memory [CALC]
32, 64 128×128, 4 —
96, 128 128×64, 4 65,536 B at head dim 128
192 128×64, 8 —
256 64×64, 4 (chosen by a run-time shared-memory test) 98,304 B

For comparison, the is_sm8x branch (Ada, RTX 30/40 series) uses 128×32 for non-causal, with the comment "128 x 32 (48 KB smem) is the fastest for non-causal since we get 2 CTAs per SM", and 64×64 for causal [SRC] :251-265.

  • Split-KV. num_splits_heuristic(batch × heads × m_blocks, num_sm * 2, num_n_blocks, 128), with the comment "We multiply number of SMs by 2 to hard-code the fact that we're using 128 threads per block" [SRC] csrc/flash_attn/flash_api.cpp:282-336. It returns 1 if the work already fills 80% of that budget, otherwise the smallest split count within 85% of the best wave-fill efficiency. Split-KV tiles are 64×128 for head dimension 128, which is 81,920 B [CALC].
  • Paged KV. Only in the split-KV kernel. Upstream requires page_block_size % 256 == 0 [SRC] flash_api.cpp:614. The vLLM fork relaxes this to % 16 with an added copy atom that gives each thread a contiguous tile, so "each thread need only fetch 1 page index per mainloop iteration" [SRC] fork csrc/flash_attn/flash_api.cpp:638; fork kernel_traits.h:135-144.

What vLLM actually passes [SRC] vllm/v1/attention/backends/flash_attn.py:1378-1403: one flash_attn_varlen_func call serves the whole batch, with the block table, fa_version=2, and num_splits=0. The fork's wrapper raises NotImplementedError("FA2 does not support num_splits > 1") [SRC] fork vllm_flash_attn/flash_attn_interface.py:251-252. With 0, the C++ heuristic runs only in the single-query GQA branch [INF] fork flash_api.cpp:757-762.

Assessment [INF]. FA2 is correct and complete on SM12x, with split-KV decode and paged KV. Its tiles are inherited, not tuned, and its split heuristic assumes two blocks per SM, which holds only for tiles of at most 50,176 B at the likely 100 KB per SM (64,512 B at 128 KB). The default head-dimension-128 tile is 64 KB, so it runs one block per SM under either reading.

4.2 FlashInfer fa2 templates

Role. SGLang's default on SM12x, and the prefill half of vLLM's FLASHINFER.

  • Dispatch. determine_attention_backend returns "fa3" only for capability major 9. Everything else, including SM12x, gets "fa2" [SRC] flashinfer/utils.py:717-730.
  • MMA. mma_sync_m16n16k16_row_col_f16f16f32 [SRC] include/flashinfer/attention/prefill.cuh:1706-1717.
  • Staging. cp.async only: load_128b_async per thread, predicated on kv_idx < kv_len [SRC] prefill.cuh:691-739.
  • Tile selection reads the device. The dispatcher reads cudaDevAttrMaxSharedMemoryPerMultiprocessor and cudaDevAttrMaxSharedMemoryPerBlockOptin, sets two blocks per SM if two minimum tiles fit, and picks the largest NUM_MMA_KV that fits both shared memory and the register bound [SRC] prefill.cuh:5005-5107. A comment names SM120 as a tight-shared-memory part [SRC] prefill.cuh:5046-5050.
  • Query tile. 128 rows if the packed query length exceeds 64 and head dimension is under 256; else 64; else 16 [SRC] include/flashinfer/utils.cuh:411-450.
  • Decode split-KV. max_grid_size = blocks_per_sm × num_sm from cudaOccupancyMaxActiveBlocksPerMultiprocessor. If the batch already fills it, no split. Otherwise a binary search finds the minimum pages per chunk. Under CUDA graphs split is always on [SRC] include/flashinfer/attention/scheduler.cuh:74-99, 175-207.
  • Prefill split-KV. Two blocks per SM is hard-coded here [SRC] scheduler.cuh:795-799.
  • Automatic upgrade to FMHAv2. In ragged prefill planning, "fa2" is rewritten to "fmha_v2" on SM120/SM121 for multi-head attention (query heads equal KV heads), head dimension 64/128/256, sequence length ≥ 256, no window, no soft cap [SRC] flashinfer/prefill.py:7016-7044. This applies to the ragged wrapper, not the paged wrapper vLLM uses.

Assessment [INF]. Unlike FA2, this kernel adapts its tile and its decode split to the device it finds. It is still cp.async with per-thread loads.

4.3 XQA decode (TensorRT-LLM port)

Role. The decode half of vLLM's FLASHINFER on SM12x, and of SGLang's trtllm_mha.

  • Gate. JIT supported_major_versions=[9, 10, 12] [SRC] flashinfer/jit/xqa.py:140-142. The C++ lists both: __CUDA_ARCH__ == 1200 || __CUDA_ARCH__ == 1210 with kMAX_SMEM_SIZE = (99u << 10) [SRC] csrc/xqa/utils.cuh:49-51.
  • Layout. 8 warps, 256 threads, warp-specialized into two groups. The CTA tile is 256 KV tokens [SRC] csrc/xqa/mha.cu:76-102. On 99 KB architectures the V tile is 32 tokens [SRC] mha.cu:114-117.
  • MMA. mma.sync.aligned.m16n8k16 in FP16 or BF16 [SRC] csrc/xqa/mma.cuh:35-50.
  • Staging. cp.async with a per-token page lookup, pageIndices[absoluteTokenIdx / tokensPerPage] [SRC] csrc/xqa/ldgsts.cuh:29-41; csrc/xqa/mhaUtils.cuh:42-43.
  • Split-KV. nbSubSeqPerSeq = min(max(1, multiProcessorCount / (batchSize * nbKHeads)), divUp(maxSeqLen, ctaTile.x)) [SRC] mha.cu:3123-3129.
  • Head dimensions. Multiples of 16 from 16 to 512 [SRC] flashinfer/jit/xqa.py:88-103. vLLM restricts XQA to 16–256 [SRC] vllm/v1/attention/backends/flashinfer.py:840-841.
  • KV dtypes. FP16/BF16, int8, FP8 e4m3, and packed NVFP4. NVFP4 is asserted SM12x-only [SRC] flashinfer/jit/xqa.py:73-80; flashinfer/xqa.py:396-399.
  • FP8 handling. Cache words are converted with cvt.rn.f16x2.e4m3x2, then multiplied as 16-bit. The Hopper FP8 tensor-core kernel is selected only for major 9 [SRC] csrc/xqa/utils.cuh:747-762; flashinfer/xqa.py:387-394.
  • Features. Sliding window, sinks, and ragged multi-token queries for speculative verification [SRC] flashinfer/jit/xqa.py:108-131; flashinfer/xqa.py:259-262. Sinks are applied in-kernel only when the request is not split [SRC] mha.cu:2618.
  • Limits. No LSE output, so no decode context parallelism [SRC] flashinfer/decode.py:4901-4916.

4.5 b12x paged attention

Role. vLLM's opt-in --attention-backend b12x. Ported into FlashInfer from lukealonso/b12x at commit 6627d342 [SRC] flashinfer/experimental/b12x/attention/paged/__init__.py:69-79. All paths below are under flashinfer/experimental/b12x/attention/paged/.

Structure. 16 files; the decode kernel is 11,267 lines, the prefill kernel 7,621 lines, the planner 2,601 lines. Three modes: decode (every request has one query token), verify (multi-token speculative verification), extend (everything else) [SRC] planner.py:72, 788-792. A plan is a flat list of work items, each a (request, query tile, KV chunk). The decode grid is one block per (work item, KV head) [SRC] planner.py:1834-1842; forward_paged.py:4178.

Support gate. Capability major 12 with minor 0 or 1, nvidia-cutlass-dsl >= 4.6.0, and Triton [SRC] flashinfer/experimental/b12x/_lib/gating.py:14-31, 89-95.

Decode and verify

  • Tile. The query tile is forced to 16 rows, giving 1 query warp × 4 KV warps, 128 threads, and a 16×64 tile. Some specializations use 16×128 [SRC] planner.py:826-832; traits.py:272-276, 464, 483.
  • MMA. Inline mma.sync.aligned.m16n8k16.row.col.f32.bf16.bf16.f32, issued twice to form a 16×16×16 step. Operands come through ldmatrix [SRC] _lib/intrinsics.py:3920-3985; forward_paged.py:1657-1682.
  • Staging is TMA only. The constructor raises otherwise: "PagedForwardKernel now only supports exact-plane paged K/V TMA decode" [SRC] forward_paged.py:3376-3382.

How the paged cache becomes a TMA source [SRC]:

  1. The cache [num_pages, page_size, kv_heads, head_dim] is re-viewed as [page_size, head_dim, kv_heads, num_pages], so the page id is the last coordinate (forward_paged.py:4077-4083).
  2. A tiled TMA atom covers (stage_tile_rows, plane_head_dim). A plane is 128 bytes per row: 64 BF16 elements or 128 FP8 bytes. A head dimension is covered by 1 to 4 planes (forward_paged.py:3427-3444, 4107-4147).
  3. One thread looks up the page and issues the copy:
page_id = mPageTable[request_idx, page_idx]
pipeline_tma.producer_acquire(producer_state)
src_idx = self._tile_src_idx_from_page_id(page_id, sub_tile)
load_tma0(src_idx=src_idx, producer_state=producer_state)

(forward_paged.py:3782-3789)

  1. A tile never crosses a page: the constructor requires page_size % cta_tile_kv == 0 (forward_paged.py:3159-3163).
  • Who issues TMA. By default no dedicated loader: warp 0 issues the next tile after releasing the consumed stage. A "role-specialized" variant adds a fifth warp that runs the loader loop, calls setmaxregister_decrease(80), and lets the math warps raise theirs to 168 or 248 [SRC] forward_paged.py:5236-5335, 5598, 6350-6366.
  • Stages. One, whenever there are multiple KV warps or the cache is FP8 [SRC] forward_paged.py:3271-3285.
  • Shared memory is read at run time. max_smem_per_sm and max_smem_per_block come from the device. A candidate gets two blocks per SM if 2 × launch_bytes <= max_smem_per_sm. Selection maximizes (residency, num_mma_kv): occupancy first, tile width second [SRC] traits.py:204-211, 308, 329.
  • Worked sizes [CALC]. BF16 decode at head dimension 128: 39,424 B, which fits twice under either reading. At head dimension 256: 73,728 B, which cannot be doubled under either reading, because 2 × 73,728 = 147,456 B exceeds even 131,072 B. (An earlier version said it could at 128 KB; that arithmetic was wrong.)
  • The residency test omits the 1 KB reservation [INF]. 2 × launch_bytes <= max_smem_per_sm does not add CUDA's 1 KB per block. On a 100 KB SM (102,400 B), a candidate of 50,177 to 51,200 B would be predicted to fit twice and would fit once. Whether any candidate falls in that range was not checked.
  • Split-KV. On under CUDA graphs with BF16 queries; always on for verify; never for extend [SRC] planner.py:2024-2039. Capacity is num_sms × graph_ctas_per_sm // num_kv_heads, where graph_ctas_per_sm comes from a shape-keyed table of 1, 2, 4 or 6 [SRC] planner.py:227-228, 493-548. Chunk budgets are table-driven by head dimension, GQA group, KV dtype and batch [SRC] planner.py:697-749.
  • Merge. A persistent kernel reduces normalized partial outputs with base-2 log-sum-exp scores. It supports only output head dimensions 128 and 256 [SRC] merge.py:1-14, 198-223; planner.py:75-84.
  • Query staging. Predicated 16-byte cp.async [SRC] forward_paged.py:890-914.

Extend (prefill)

  • Query tile. 16 if the packed query length is ≤ 32, otherwise FlashInfer's FA2 rule (128, 64 or 16) [SRC] planner.py:795-801, 833-835.
  • Staging is mostly cp.async. TMA is enabled for one shape only: BF16, head dimension 256, 16-row query tile, page size 64. The comment: "Page-128 uses the byte-addressed copy path until extend TMA gets the decode kernel's page-entry flattening" [SRC] forward_extend_generic.py:3272-3290. Otherwise every thread does a per-row page-table lookup and a 16-byte cp.async [SRC] forward_extend_generic.py:3836-3870.
  • No split-KV [SRC] planner.py:2038-2039.

FP8, sinks, window, GQA

  • FP8 KV is converted, by default. Bytes are TMA-staged raw, loaded with ldmatrix, converted in registers, then multiplied as BF16 [SRC] forward_paged.py:1680-1709.
  • Native FP8 multiply is opt-in through B12X_TURBO_ATTN=1, and for decode is further limited by batch and chunk thresholds [SRC] _forward.py:78-79, 164-192. The instruction is mma.sync.aligned.kind::mxf8f6f4.block_scale.scale_vec::1X.m16n8k32 [SRC] _lib/intrinsics.py:4019, 4083.
  • Sinks. attention_sink_bias[q_head] is folded into the running softmax state as an extra logit, by one warp, and under split-KV only by the chunk that owns the causal limit [SRC] forward_paged.py:977-1011.
  • Sliding window. Converted to a per-request window start page by the planner [SRC] planner.py:198-213, 2070-2086.
  • GQA packing. Query rows for heads sharing one KV head are packed together. One block serves one KV head and all its query heads [SRC] forward_paged.py:3909-3920.

Why head dimension 64 fails

vLLM excludes head dimension 64 "until flashinfer-ai/flashinfer#6977 is fixed" [SRC] vllm/v1/attention/backends/b12x.py:203-206. The issue title: "experimental/b12x paged attention cannot plan head_dim 64 decode: trait rule and decode kernel contradic[t]" [ISSUE] [S20].

The mechanism [INF from SRC]:

  1. Head dimension 64 means num_mma_d_vo = 4 (traits.py:199).
  2. Decode forces a 16-row query tile, and for that tile the candidate sweep tries only num_mma_kv = 1 (traits.py:272-276).
  3. A trait rule rejects num_mma_d_vo == 4 and num_mma_kv % 2 == 1 (traits.py:88-105).
  4. The sole candidate is rejected, raising "no valid NUM_MMA_KV typed shared-memory allocation fits the device" (traits.py:319-322).

Independently, the split-KV merge requires output head dimension 128 or 256.

SM121 and fences

  • Tile specializations are keyed on exactly (12, 0). Five trait specializations and one planner budget test device_capability == (12, 0); two use >= 12 [SRC] traits.py:383, 411, 440, 459, 468, 486, 533; planner.py:272. On a Spark the generic sweep is used [INF].
  • No fence_proxy call appears in the paged attention files [SRC, by grep]. Fences are used elsewhere in b12x. Section 8.3 discusses whether that is a risk.

4.6 Upstream FlashAttention-4 on SM120 (main)

Role. Not reachable from vLLM. Documented here because it is the base that open pull requests extend.

5.2 FLASH_ATTN on capability 12

  • Version. FA3 if major 9; FA4 if major 10; otherwise FA2 [SRC] vllm/v1/attention/backends/fa_utils.py:91-100.
  • What FA2 cannot serve, and the reason string [SRC]:
  • Sinks. supports_sink() is true only for FA3 or FA4 (flash_attn.py:422-426; fa_utils.py:244-247).
  • FP8 KV. "FP8 KV requires FA3 (SM90), equal-d512 FA4 (SM90), or FA4 (SM100)." (flash_attn.py:464-474).
  • Multimodal prefix. Requires FA4 (flash_attn.py:418-420).
  • What it serves: sliding window, non-causal attention, batch invariance, decode context parallelism, head sizes up to 256 that are multiples of 8, block sizes that are multiples of 16 [SRC] flash_attn.py:332-406, 1038.
  • CUDA graphs. FA2 reports UNIFORM_BATCH, not ALWAYS, because FA2 has special packed-GQA handling for single-token queries [SRC] flash_attn.py:578-597.

Consequence [INF]. On SM12x, automatic selection yields FA2 for a plain BF16 model and FLASHINFER as soon as the model needs FP8 or NVFP4 KV, sinks, or a multimodal prefix.

Forcing FA4. The gate is in vLLM's tree: "FA4 is only supported on devices with compute capability 9.x, 10.x, or 11.x" [SRC] vllm/vllm_flash_attn/flash_attn_interface.py:72-86. With --attention-config.flash_attn_version=4 on capability 12, get_flash_attn_version logs "FlashAttention 4 is not supported (...); it will not be used.", fails an assertion that is caught, and returns None [SRC] fa_utils.py:189-199. Validation does not require a version, so the backend is still selected, and the first forward pass fails on "FlashAttention version not detected." [INF from SRC] flash_attn.py:1201-1203. Expected outcome: a startup failure, not a silent fallback. Not run.

5.3 FLASHINFER on SM12x

Capability window. >= (8, 0) and <= (12, 1) [SRC] vllm/v1/attention/backends/flashinfer.py:779-781.

Prefill. supports_trtllm_attention(is_prefill=True) is false on the SM12x family, so prefill always uses BatchPrefillWithPagedKVCacheWrapper(..., backend="auto") [SRC] vllm/utils/flashinfer.py:884-887; flashinfer.py:1573-1581. In FlashInfer, "auto" resolves to "fa2" for any capability major other than 9 [SRC] flashinfer/utils.py:717-730. vLLM's own comments call SM12x prefill "fa2-only" [SRC] flashinfer.py:1276-1277.

Decode uses XQA only if all of these hold [SRC]:

  1. --attention-config.use_trtllm_attention is not false.
  2. VLLM_BATCH_INVARIANT is unset.
  3. has_nvidia_artifactory() is true. That is: the flashinfer_cubin package is importable, or VLLM_HAS_FLASHINFER_CUBIN=1, or an HTTP request to the cubin repository returns 200 within 5 seconds (vllm/utils/flashinfer.py:61-64, 85-92, 840-864).
  4. Query heads are a multiple of KV heads.
  5. Head dimension is 16 to 256 in steps of 16 (flashinfer.py:840-841).
  6. Decode context parallelism is off (flashinfer.py:1122-1132).

Otherwise decode uses BatchDecodeWithPagedKVCacheWrapper with tensor cores and backend="auto" [SRC] flashinfer.py:1626-1645.

Consequence [INF]. On an air-gapped Spark without the cubin package, XQA is silently off. Sinks then become unsupported, because sink support on SM12x is defined as XQA being available [SRC] flashinfer.py:783-796, and CUDA-graph support drops from UNIFORM_BATCH to UNIFORM_SINGLE_TOKEN_DECODE [SRC] flashinfer.py:1309-1352.

Query dtype on SM12x [INF from SRC] flashinfer.py:1264-1305: the model dtype in every case. With an FP8 cache, "Architectures with only fa2 (e.g. SM89, SM120) cannot consume FP8 queries". With XQA, "requires BF16/FP16-Q even with FP8 KV cache".

Other SM12x specifics [SRC]:

  • Block sizes 16, 32, 64. Sizes of 128 and above are advertised only on the SM100 family (flashinfer.py:595-612).
  • NVFP4 KV: only the literal nvfp4 dtype; head size 64 and sinks are refused; decode context parallelism and non-causal attention raise (flashinfer.py:727-759, 1048-1051, 1517-1521).
  • Multimodal prefix: served natively by BatchPrefillWithCausalBidirectionalRangesWrapper (flashinfer.py:1585-1603).
  • Speculative verification: ragged multi-token queries stay on the XQA decode path with a packed draft mask (flashinfer.py:1465-1506, 1731-1743).
  • Batch invariance: FLASHINFER fails validation (backend.py:221-223).

  • Observation: the paged attention files contain no fence_proxy call.

11. Research path

11.1 Framing

The earlier version of this plan proposed inventing page-aligned TMA staging and SM12x split-KV. Both exist. The questions that remain open are narrower and better defined:

  1. Which existing kernel wins for which workload on each machine, measured on one harness.
  2. Whether the DGX Spark's limit is memory bandwidth, and what follows if so.
  3. Where the unfinished pieces are: prefill staging on a paged cache, native FP8 in the paths the engines actually call, Spark-specific tuning, and dispatch.

11.2 The bandwidth argument for the Spark

Arithmetic [CALC]. A hypothetical model with 32 layers, 8 KV heads and head dimension 128 stores 8 × 128 × 2 × 2 = 4,096 bytes per token per layer in BF16. That is 128 KiB per token, and 4 GiB at a 32,768-token context. One decode step reads all of it.

Cache Bytes read per step Floor at 273 GB/s (Spark) Floor at 1,792 GB/s (RTX PRO 6000)
BF16 4.29 GB 15.7 ms 2.4 ms
FP8 2.15 GB 7.9 ms 1.2 ms
NVFP4 (≈4.5 bits) 1.21 GB 4.4 ms 0.7 ms

These are floors for reading the cache once. They ignore compute.

Hypothesis A. On the Spark, long-context decode is bandwidth-bound for every kernel. Kernel choice matters little; cache precision matters almost linearly.

  • Supporting evidence: SGLang's integrated-GPU comment (section 10.3); the smaller GB10 gains in section 9; the bandwidth ratio (6.6×) exceeding the SM ratio (3.9×).
  • Falsified if: two BF16 kernels differ by more than about 20% at batch 1 and a 32K context on the Spark.

Hypothesis B. On the RTX PRO 6000, batch-1 decode is occupancy-bound, so split-KV and tile choice matter.

  • Supporting evidence: #3109's 2.54× decode gain over an unsplit baseline; #2980's worst case of 0.43× at batch 32, where splitting should not help.
  • Falsified if: achieved bandwidth is already near 1,792 GB/s without split-KV.

11.4 Phase 1 — Harness

  • Record per run: capability; engine and library commits; the log lines of section 5.5; head dimension; query-to-KV head ratio; page size; KV dtype; query length, KV length, batch.
  • Correctness oracle: FP32 scaled_dot_product_attention on a de-paged copy. Per-row maximum absolute and relative error with a per-dtype tolerance. For scale: SGLang #32991 reports a maximum absolute difference of 0.0078 on RTX cards and 0.0156 on GB10 against Triton.
  • Edge cases: lengths at page size ± 1; contexts long enough to recycle every pipeline slot; sinks under split-KV (b12x applies the sink only in the chunk owning the causal limit; XQA applies sinks in-kernel only when not split).
  • Stress gate: every case under CUDA-graph replay with a copy and matmul on a second stream, the pattern from FlashInfer #7675.
  • Two levels: a kernel microbenchmark and a served benchmark with time to first token and inter-token latency reported separately.

11.8 Phase 5 — Prefill staging on a paged cache

  • Finding: decode has page-aligned TMA in b12x and in one SGLang specialization. Prefill does not. b12x extend uses per-thread cp.async with a per-row lookup; its own comment names the missing piece ("until extend TMA gets the decode kernel's page-entry flattening"). SGLang uses a cp.async gather with a loader warp.
  • Question: for prefill, does TMA with the page id as a coordinate beat the cp.async gather at 99 KB with mma.sync consumers?
  • Design constraint: the page size must be a multiple of the KV tile. Page 64 with a 64-row tile, or page 128 with sub-tile addressing as b12x decode does.
  • Reference for cost: FA #2348 reports paged at 1.09–1.18× the dense time on GB10 with cp.async; FA #2980 reports paged FP8 at 0.883× of contiguous.
  • Gate: phase-1 stress test, with attention to the fence question of section 8.3.

11.9 Phase 6 — Native FP8 in the paths the engines call

  • Finding: native FP8 multiply exists in b12x (opt-in), FA #2980 and #3132 (open), SGLang #45871 (open). vLLM's FLASHINFER path converts FP8 to 16-bit. Reported gains are 1.7–2.0×, all on RTX PRO 6000.
  • Experiments:
  • BF16 KV, FP8 converted, FP8 native, on both machines.
  • B12X_TURBO_ATTN=1 against the default, with the batch and chunk thresholds that limit it for decode.
  • Accuracy against the FP32 oracle and a task metric, reported separately from speed.
  • Why the Spark matters here: if hypothesis A holds, converted FP8 already halves the bytes read, and native FP8 adds little for decode. If native FP8 still helps on the Spark, decode there is not purely bandwidth-bound.
  • Technique to note: both #3132 and #45871 scale P by 2⁸ before the FP8 cast so that probabilities use the format's range.

11.11 Phase 8 — Dispatch

  • Finding: vLLM picks by validity. Its SM12x default is FA2, and b12x is unreachable without a flag.
  • Deliverable: a rule per machine, phase and KV dtype, backed by phase-2 tables. SGLang's per-phase flags can run such a rule today. vLLM needs it in _get_backend_priorities.
  • A caution from the data: #2980's BF16 decode was slower than FA2 in 47 of 108 shapes. A blanket "prefer the new kernel" rule would regress nearly half of them.

11.12 Order

Phases 0–2 are prerequisites. After that the order depends on which hypothesis survives:

  • A holds (Spark is bandwidth-bound): phase 6 first on the Spark, then phase 4.
  • B holds (RTX PRO 6000 is occupancy-bound): phases 3 and 5 first on the RTX PRO 6000.

13.2 Documentation that lags the code

  • vLLM docs call XQA "the SM90 decode path" and say the FlashAttention default is "FA2 otherwise"; the code enables XQA on the SM12x family [SRC] docs/design/attention_backends.md:176-178.
  • vLLM docs list FlashInfer capability as 8.x–9.x, 9.0 and 10.x; the source accepts up to 12.1.
  • vLLM docs list b12x KV dtypes as auto and capability "Any"; the source accepts BF16 and FP8 and exactly (12, 0) and (12, 1).
  • SGLang docs list FA4's native page size as 128 with no qualifier; the forcing is SM100-only.
  • SGLang docs say Blackwell defaults to trtllm_mha; that is SM100 only.
  • SGLang docs say trtllm_mha is decode-only for hybrid GDN models on SM120; the assertion allows prefill.
  • SGLang docstring in get_default_attn_backend says "trtllm_mha does not support SM120"; the validation code accepts it.
  • The author's vault note "Writing FlashInfer Kernels for DGX Spark GB10" says "FA4 is tcgen05-only → SM100 only". Upstream has had an mma.sync SM120 path since March 2026.

13.3 Disagreements between primary sources

  • Shared memory per SM, capability 12: 128 KB (tuning guide) against 100 KB (programming guide). The evidence favours 100 KB (section 2.5); a device query would settle it.
  • Thread blocks per SM, capability 12: 32 against 24, same two documents. The tuning guide gives 32 in a sentence shared with 10.0, which suggests it was carried over; 24 is more likely, and 24 two-warp blocks exactly fill the 48-warp limit. Both guides agree on 48 warps for 12.x; the 64 belongs to 10.0.
  • Minimum toolkit for DGX Spark: CUTLASS's README says CUDA 13.0; its config.h enables SM121 from 12.9.
  • FA #2998's body says can_implement rejects head dimension 256; no call to can_implement was found on the forward path at 9f9742c.
  • FA #3109's body describes main's SM120 path as "fixed 64 × 64 tiles"; that matches the backward kernel, not the forward.

13.5 The smallest experiment that would change the plan

On each machine, serve one BF16 head-dimension-128 model twice: with no flag (FA2), and with --attention-backend b12x. Confirm each backend from the log lines in section 5.5. Measure batch-1 inter-token latency at a 32K context.

  • Near-equal on the Spark, clearly different on the RTX PRO 6000: hypotheses A and B both stand. Do phase 6 first on the Spark and phases 3 and 5 first on the RTX PRO 6000.
  • b12x clearly faster on the Spark too: decode there is not purely bandwidth-bound. Phase 4 (Spark tuning) moves ahead of phase 6.
  • FA2 faster on the RTX PRO 6000: consistent with #2980's finding that new BF16 kernels lose to FA2 on many decode shapes, and a reason to treat phase 8 (dispatch) as the main deliverable.
